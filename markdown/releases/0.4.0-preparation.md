## Basis performance

A subsequent [basis investigation](../basis-update/performance-2026-10-06.md)
separates the regressions by commit, measures optimization prototypes, and fixes
a missing library-graph extension in the phase profiler. The older samples below
are retained as release-preparation observations, not the final diagnosis.

A same-source small-program probe ran `checkSource`, `analyzeVirtual`, and
`compile` against the pre-basis revision `fb56ea6` and the current checkout.
Times exclude process launch and module import. These are indicative local
samples, not a controlled basis-only A/B: the current checkout also has syntax
changes, and background release/test work can affect timing.

| Operation | Before basis move | Current before optimization | With scope reuse |
| --- | ---: | ---: | ---: |
| First check in a process | 459 ms | 960 ms | 1,079 ms |
| Warm check | 2.0–2.2 ms | 3.3–4.9 ms | 3.5–4.3 ms |
| Warm editor analysis | 2.6–4.1 ms | 31.9–34.5 ms | 21.7–27.8 ms |
| Warm compilation | 9.4–11.0 ms | 28.6–38.5 ms | 17.1–21.0 ms |

CPU sampling identified `snapshotBindingEnv` as a substantial cost. An environment
is populated before traversal and cloned when bindings change, so nodes sharing
an unchanged environment now reuse one scope snapshot instead of copying four
maps repeatedly. Existing scope, completion, definition, rename, and shadowing
checks passed (47 tests).

The first standard-library load is still expensive. The webhook phase profiler
averaged 717 ms over three iterations, of which 321 ms was standard-library load
(the cold cost is amortized in that average). Parsed/inferred library modules are
already cached per process; whole-program facts for the expanded library are
still rebuilt. Caching those facts needs a design that preserves per-program
binding/type identities and is a follow-up, not a safe blanket cache to add here.

The current tiny LSP typing benchmark completed 81 edits: initial diagnostics
1,190 ms; edit-to-diagnostics p50 76 ms, p95 84 ms, max 88 ms. This establishes a
current baseline; it is not a before/after editor benchmark.

6m23s: **1,090 passed, eight failed, one ignored**. Seven failures were corrected
and verified with focused reruns: one stale diagnostic line, two missing GPU
runtime helper cases, three stale pattern-fact expectations, and one stale
recursion-fact expectation. The complete suite has not been rerun after these
fixes; do not describe the final tree as having a passing full-suite run.

Focused checks after the new fixes:
47 binding/LSP tests, three basis runtime/parity checks, and six WebGPU render tests
passed. The stale `Result.debug` diagnostic line expectation was updated and its
focused check passed. Pattern/recursion tests now distinguish authored module
facts from ordinary library-module facts; all six focused checks passed.
Typechecking and ten VS Code extension tests passed.

The subsequent plain-source/no-prelude optimization passed 221 focused compiler,
FFI, basis, discovery, and LSP tests plus typechecking. The local 0.4.0 VSIX was
rebuilt successfully with those changes. Library scope reduction was declined;
pre-parsed library ASTs are deferred until after the parser rewrite.

Staging review: the complete `deno task check` and the generated-recognizer
reproducibility check passed against an isolated copy of the staged tree. The
release stage excludes v3 development, scratch files, and unrelated design/issue
notes. No commit was made.

The full run found a formatter failure for `examples/c_ffi/vector3.wm` in the
example semantic-golden test: parsing succeeds but formatting returns `None`.
Formatter work remains deferred; this failure is still an open release decision.

The machine-specific `byte_type` dependency is resolved: the clean local fork at
`56cdc7b28a064c85ee3f9a681d48149776f7a02d` is vendored in
`src/vendor/byte_type`, with all production modules and its MIT license.
Compile-time checks resolve that tree; generated C codec programs embed a
self-contained JavaScript bundle with the license notice. Ordinary generated
programs omit that bundle. The VSIX also carries the license separately.

Vendoring verification: 93 scoped compiler/frontend/library/LSP and codec checks
passed, along with the complete typecheck in an isolated staged-tree copy and
the runtime bundle regeneration check. The C Vector3 example compiled and ran
from `/tmp`, producing `1` and `32`. A subprocess regression loads the codec
bundle without file/network permissions or repository configuration. Generation
and the 0.4.0 VSIX build succeeded; packaged parser/compiler files and the license
were checked against the source tree, and the bundled LSP startup smoke passed.

The C header extractor template is embedded in generated assets, so packaged
compilers do not need to fetch a sibling `.zig` file. The legacy backend uses
system Zig 0.16.x via `WM_ZIG_PATH` or PATH. Linux uses an explicit host-architecture
GNU target to avoid incompatible host CRT files. Version and host target are
included in cache keys; version probes are reused per compiler process.

A beta standalone Aro backend now reads arbitrary headers at runtime and emits
reflection JSON directly, without translating or compiling a Zig header program.
`deno task c-header:build` builds against Aro in the pinned Zig 0.16.0 distribution
for Linux/macOS/Windows on x64 and ARM64. Compressed JavaScript payloads ship in
JSR and the universal VSIX. Automatic platform selection loads only the matching
asset on first C reflection, verifies checksums and atomically unpacks it with
resource headers and licenses. Runtime users need no Zig or separate binary download.
The main CLI and Fresh's `wm lsp` use the same packaged assets. Native results
hash transitive includes for cache invalidation. Beta limits remain for unions,
bitfields, anonymous fields and variadic/old-style functions; the explicit
`WM_C_HEADER_BACKEND=zig` compatibility path remains available. WASM is deferred.
Generation and the local publish task build all six targets; CI checks the
committed payloads against source/resources/checksums without rebuilding Zig.

System-Zig follow-up: C reflection now uses filesystem/process APIs supported by
both Deno and Node, including local library discovery. Fourteen dependency,
codec, and LSP checks passed, as did typechecking and the Vector3 compile smoke.
A direct Node extraction confirmed size 12 and offsets 0/4/8. The rebuilt
packaged Node LSP opened a C-header program and published zero diagnostics.
Linux was verified; macOS/Windows defaults remain unverified. No Zig binary is
included in the 0.4.0 VSIX.


Aro follow-up verification: six native extractor tests, eight LSP diagnostic tests,
and eight fallback/codec/compiler tests passed. Native tests and the Vector3 run
used an intentionally missing `WM_ZIG_PATH`. Vector3 printed `1` and `32`; selected
Vector3/V2 function, layout and macro JSON exactly matched the Zig backend. The
rebuilt VSIX's Node server published zero diagnostics with the native override.
A single reflection-cache-miss comparison took roughly 7 ms for Aro versus 185 ms
for Zig with its compilation cache already warm; this is a smoke measurement,
not a cold-start benchmark. Full tests were not repeated for this follow-up.

Twenty focused extractor, legacy dependency, codec and LSP tests passed with Zig

The rebuilt universal VSIX is 7.28 MB (131 files). Main toolchain/LSP and build/check

The complete local `deno task publish` finished successfully with the new native
